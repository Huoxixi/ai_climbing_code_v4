## 服务器运行范围

`deploy/browser/profile.json` 明确为 `browser-only`。GitHub 保有完整 App；生产发布包由 `prepare_release.py` 白名单生成，仅含独立网页、浏览器固定模型/运行组件、安装包下载及轻量静态/健康后台。不会把整个 GitHub 项目安装为生产后台。

网页免账号，自动校验/缓存本机模型，用户电脑计算；视频与历史留在 IndexedDB，导出也在浏览器完成。旧照片、账号、上传、服务端算法 API 在新后台返回 404。网页仍使用现有 2026.10.10 在线安装包下载，最新实际程序快照另存私有 GitHub Release，二者版本含义不同。

模型固定为 YOLOX/RTMW 原权重 265,319,892 字节，按大小和 SHA-256 校验。运行模块使用 `.js` 输出，适配已有 Nginx JavaScript MIME 配置。WebGPU 未在本轮证明，实际模型和视频导出以 CPU/浏览器实测为准。

## 发布和清理顺序

1. 本地及 GitHub PR 的 `release-gate` 通过后纳入 main，创建新的不可变 `pilot-vYYYY.MM.DD-rcN` 标签，再核验标签门禁。
2. 受限 SSH 可 status/releases/code-status/deploy，无法任意 shell。因此首次更新发布分发器和旧项目清理，需要已授权 root 终端执行经门禁审核的脚本；不扩大受限密钥权限。
3. `retire_legacy_project.py prepare` 先用原备份脚本生成并验证远端 pre-deploy 备份，保留当前 rc29，清理旧的非运行 rc26/rc28。仅在旧构建树与已核验旧提交一致且无修改时，保存程序源码归档并清理旧 Git 元数据及构建依赖。个人资料和环境文件排除。
4. 仍要求至少 8 GiB 空间；不足时停止，当前旧站继续运行。不会为腾空间删除业务数据或备份。
5. `install_release_dispatcher.sh` 仅更新原发布入口，保留原服务器部署脚本；不重装 Nginx/systemd，不改生产凭据或业务配置。之后依旧通过 `/usr/local/lib/ai-climbing/deploy_release.sh <完整标签>` 发布。
6. 新版发布先实际检查模型、网页、导出、下载和关闭旧 API，失败自动恢复旧程序。确认新版运行后，`retire_legacy_project.py finish` 删除剩余旧运行程序，把旧模型和测试材料移入私有备份目录，保留 `/var/lib/ai-climbing/data`、`/etc/ai-climbing` 及既有备份。

最新用户明确要求清理旧项目，因此此前“在线保留三个旧完整 App 版本”的保留策略在本轮被旧项目退役流程覆盖。生效的新版网站及它的 GitHub 标签保留；旧业务数据不随程序退役而删除。
