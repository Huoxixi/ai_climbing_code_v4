## 0. 本次重构依据

本版不是对旧 PRD 做供应商名称替换，而是依据当前代码和最新技术验证文档重新划定产品能力。

已核实的技术变化：

| 项目 | 旧技术验证 | 当前技术验证 | PRD 影响 |

## 1. 结论先行

### 1.1 产品结论

本项目值得继续，建议将其建设为“我的记录”中的独立模块 **AI 攀岩复盘**，而不是塞入“照片识别线路”的默认流程。

用户上传一次攀岩视频后，系统完成视频质量检查、岩点识别、人体姿态估计、手脚接触事件提取、动作指标计算和人工校正；保存为一次私密攀爬记录。用户积累多次记录后，可以在同一线路、相似机位和相似拍摄条件下比较动作效率、稳定性与风险观察项。

产品对外应表述为：

> 基于视频的动作复盘与风险观察工具，帮助用户发现可复查的动作变化；不测量真实肌肉力量，不替代教练、医生或康复师判断。

### 1.2 使用权结论

移除 VLM Run 后，现有原型的数据边界更清晰，可以继续用于所有者本人或明确授权测试者的非公开验证；但在下列阻塞项完成前，仍不批准商业公开上线：

1. 阿里云视觉智能开放平台的服务协议、隐私政策、计费快照、地域和数据处理说明尚需纳入项目合规档案；公开说明不能替代正式合同和本项目的数据处理评估。
2. 当前岩点识别使用服务器本地专项 Mask R-CNN，人体姿态使用阿里云 BodyPosture。自有模型代码、模型权重与训练数据权利，以及阿里云 SDK 许可证和云服务合同必须分层登记。VLM Run、SAM 3.1 与 ViTPose+ Large 不再是当前上线依赖。
3. 用于训练或评测的攀岩视频、人体姿态数据集，除数据许可证外，还需核对人物肖像、场馆拍摄、研究受试者同意和商业训练权限。
4. 当前仓库根目录未发现项目级 `LICENSE`。这不妨碍权利人内部使用自己的代码，但第三方不能据此推定获得复制、修改或商业分发许可；对外发布前需要由权利人明确授权策略。
5. 任何包含 Ultralytics YOLO 的方案，不得在闭源商业产品中直接采用，除非接受 AGPL-3.0 的完整义务或购买企业许可。
6. 任何包含 Facebook VideoPose3D 的现成链路，不得直接进入商业版，因为其官方许可为 CC BY-NC（非商业）。
7. 安全输出只能是“可观察事件与复查建议”，不得输出伤病诊断、受伤概率、可继续攀爬保证或治疗建议。

### 1.3 推荐技术方向

采用“本地岩点识别、国内逐帧姿态、人工可校正”的混合架构：

- 岩点与路线：优先复用现有照片线路的用户确认结果；没有已保存线路时，使用服务器本地专项 Mask R-CNN，并强制用户确认。
- 姿态估计：视频按默认 4 FPS 抽帧、压缩后调用阿里云视觉智能开放平台 BodyPosture；完整视频不发送给姿态服务。
- 第三方处理：仅在用户本次明确同意后发送降帧画面；默认使用上海地域，服务端密钥由专用 RAM 子账号提供。不得把完整视频、线路库或历史记录发送给姿态服务。
- 自建替代：后续只将 MediaPipe、MMPose/RTMPose 等许可证清晰且通过独立验证的方案作为降本或离线候选，不进入当前默认链路。
- 所有 AI 结果先标为“待复核”，人工修正后才进入长期趋势统计。

## 2. 背景与问题

攀岩者通常用手机录下尝试，但视频很快沉没在相册中。仅凭记忆，很难回答：

- 同一条线路是否真的更流畅、更省动作？
- 哪些岩点发生了重复换手、犹豫或脚滑？
- 重心移动、左右侧使用、静止时间是否在改善？
- 哪些动作值得请教练重点复查？
- 疼痛、疲劳或不稳定感是否与特定动作反复同时出现？

现有项目已经具备独立 AI 复盘原型：账号隔离的视频上传、分片与续传、后台分析任务、取消与重试、服务器本地专项模型识别颜色线路、阿里云 BodyPosture 姿态估计，以及完攀、用时、岩点顺序、手脚接触和身体中线等结果。

原型的主要缺口不是“能不能跑”，而是：

- 结果缺少逐帧可视化与人工纠正闭环；
- 目前的接触判断主要基于关键点与岩点框重叠，尚未达到像素级、可验证的接触判定；
- 缺少正式的长期记录、同线路对比和趋势定义；
- 缺少原视频保存/处理副本删除策略；
- 缺少模型、数据和云服务的完整权利链；
- 缺少真实视频集上的准确率、误报率、成本和性能验收。

### 2.1 当前实现的事实边界

当前实现可作为后续产品的技术底座，但结果仍是 `prototype_needs_review`，其算法事实如下：

1. 从视频九个时间位置取帧，使用中位数画面估计无人物墙面背景；人物长时间遮挡岩点时可能影响背景与岩点识别。
2. 本地专项 Mask R-CNN 生成岩点掩膜，再根据轮廓内颜色筛选目标线路；当前接触计算仍使用掩膜外接框，而不是像素掩膜。
3. 视频以 1–10 FPS 可配置抽帧，默认 4 FPS；每帧最长边缩放到 1280 像素，JPEG 质量 82，单张不得超过 3 MB。
4. BodyPosture 返回 18 个二维关键点；系统转换到现有 17 点结构，`neck` 不进入当前接触算法。
5. 多人画面逐帧选择关键点覆盖面积最大的主体，当前没有稳定的跨帧人物身份跟踪，不能保证拥挤画面始终分析同一个人。
6. 手脚关键点落入岩点外接框（含小范围边距）并持续约 0.4 秒后，才确认接触。
7. 起步时间暂按“首次同时存在稳定手点与脚点接触”估算；完攀暂按“双手同时接触最高识别岩点”估算。
8. 4 FPS 足以验证静态接触顺序，但可能漏掉快速动态动作、瞬时脚滑或碰撞峰值；当前不得据此提供危险动作判定。
9. 前端复选框目前会阻止未勾选用户提交，但上传请求没有携带或持久化同意版本、供应商、地域和时间；当前尚不构成可审计的授权记录。

因此第一版产品核心是“生成一份可校正的复盘草稿”，不是“自动教练”或“安全诊断器”。

### 3.1 必须保持独立的两条链路

| 模块 | 用户问题 | 当前稳定职责 | 本 PRD 是否修改 |
|---|---|---|---|

| AI 攀岩复盘 | “这次怎么爬的？多次是否在改善？” | 视频分析、动作事件、人工复核、历史比较 | 是。本 PRD 的建设范围 |

两者只通过稳定的已保存线路 ID 建立可选关联。AI 复盘失败不得污染照片线路，照片线路也不得因复盘模型变化被自动重写。

## 4. 产品目标与非目标

### 4.1 产品目标

1. 让用户每次上传或拍摄攀岩视频后，获得一份可看懂、可修正、可保存的动作复盘。
2. 将多次视频转化为结构化记录，在可比条件下展示变化趋势。
3. 用可追溯的时间点和画面证据提示“值得复查的动作”，减少只有一句抽象评分的黑箱体验。
4. 保护用户视频、身体数据和健康相关反馈，默认私密并可删除、可导出。
5. 保证照片线路主链稳定，复盘能力以独立模块逐步上线。

### 4.2 非目标

第一至第二阶段不做：

- 不估算真实抓握力、肌肉力、关节力矩或肌腱负荷；普通单目视频不支持可靠测量这些量。
- 不输出医学诊断、伤病概率、康复方案或“安全可爬”结论。
- 不自动评价线路难度。
- 不根据单次视频给用户贴“动作差”“受伤型选手”等标签。
- 不把不同线路、不同机位、不同镜头焦距的视频直接汇总成一个虚假的综合进步分。
- 不默认公开、分享或用用户视频训练模型。
- 不自动把记录或标注同步到 GitHub 等公开代码平台。
- 不在第一版实现多机位 3D、力传感器、IMU 或 OpenSim 动力学分析。

## 5. 目标用户与核心场景

### 5.1 目标用户

| 用户 | 核心需求 | 第一版优先级 |
|---|---|---:|
| 经常抱石的个人用户 | 记录尝试、比较同线路动作变化 | P0 |
| 初中级攀岩者 | 看懂手脚顺序与犹豫，并复查自己标记的脚滑和身体摆动 | P0 |
| 教练或训练伙伴 | 基于具体帧沟通，而不是依赖口述 | P1 |
| 场馆/训练团队 | 多成员训练档案和授权管理 | P2，商业版再评估 |
| 运动科研人员 | 3D、动力学和数据导出 | P3，研究模式 |

### 5.2 核心用户故事

- 作为攀岩者，我可以上传一个固定机位视频，系统告诉我是否适合分析。
- 我可以选择已有照片线路，或指定目标岩点颜色并人工确认线路。
- 我可以在时间轴上看到系统生成的手脚接触、换手和长时间停顿候选，并手工标记脚滑或失控摆动。
- 如果 AI 识别错了，我可以改岩点、接触肢体、事件起止时间和完攀状态。
- 我确认后，这次记录才进入历史趋势。
- 我可以只比较同一条线路和相似拍摄条件下的多次尝试。
- 我可以记录主观用力、疼痛/不适位置、疲劳和当日状态，并控制这些信息是否参与复盘。
- 我可以删除原视频、只留结构化指标，也可以删除整次记录并导出自己的数据。

## 6. 核心流程

```text
选择或拍摄视频
  ↓
本地预检：格式、时长、清晰度、人物完整度、镜头稳定性
  ↓ 不合格
给出可操作的重拍建议，不进入阿里云姿态调用
  ↓ 合格
选择已有线路 / 颜色 / 手工圈选岩点
  ↓
展示处理方式与数据去向 → 用户同意本次抽帧姿态处理
  ↓
后台分析：本地岩点 → 阿里云抽帧姿态 → 接触事件 → 基础指标
  ↓
结果可视化：叠加视频、时间轴、事件卡片、置信度
  ↓
用户修正并确认
  ↓
保存私密记录
  ↓
同线路历史比较与趋势
```

### 6.1 拍摄指引

上传前展示 10 秒可读完的指引：

- 手机固定，尽量正对岩壁；
- 全程包含手、脚和目标线路；
- 避免强逆光、多人严重遮挡和频繁变焦；
- 开始前静止 1 秒，结束后保留 1 秒；
- 尽量复用相同机位，才能进行可靠的历史比较；
- 确保视频中的其他人同意被拍摄，或使用自动打码。

## 7. 功能需求

本章每个任务均在 7.8 标注需要借鉴的仓库、论文或官方依据。编号、完整书目信息、许可证边界、可借鉴内容和未来论文用途统一维护在 `docs/AI攀岩复盘_研究证据与引用台账_2026-09-20.md`。标注为“产品/工程定义”的任务来自业务、可靠性或隐私要求，不表示已有论文替本项目完成了验证。

### 7.1 视频采集与任务管理

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---:|---|
| FR-001 | 支持 MP4 上传、分片、断点续传 | P0 | 网络中断后可继续；重复分片不产生重复任务 |
| FR-002 | 执行格式、大小、时长、帧率、分辨率和编码检查 | P0 | 沿用当前 200 MB、90 秒、2700 帧等上限，配置可调整 |
| FR-003 | 执行清晰度、镜头抖动、人物完整度、遮挡和视角预检 | P0 | 不合格时给出具体重拍建议 |
| FR-004 | 后台任务可查看进度、取消、失败重试 | P0 | 取消后停止后续抽帧调用；重试记录新的调用批次，不能把失败重试伪装为零成本 |
| FR-005 | 每个账号默认仅运行一个分析任务 | P0 | 其余排队；用户可删除排队任务 |
| FR-006 | 用户可选择是否保留原视频 | P0 | 未选择保留时，处理副本按保留策略自动删除 |
| FR-007 | 记录本次第三方处理同意 | P0 | 当前仅有前端复选框，需新增服务端记录：告知版本、供应商、地域、数据种类、时间和撤回结果；不预勾选 |
| FR-008 | 姿态服务不可用时允许保存未分析视频或进入手工模式 | P1 | 密钥缺失、欠费、限流或超时不导致用户原视频和备注丢失 |

### 7.2 线路与岩点

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---:|---|
| FR-101 | 关联一个已保存照片线路 | P0 | 只读引用，不自动修改原线路 |
| FR-102 | 没有线路时可选择岩点颜色 | P0 | 显示颜色选择与置信度，不把相近颜色强行合并 |
| FR-103 | 支持用户增加、删除、移动、调整岩点轮廓 | P0 | 修正记录留痕，分析指标随修正可重算 |
| FR-104 | 支持标记起步点、终点和禁用岩点 | P1 | 计时和完攀逻辑使用用户确认后的定义 |
| FR-105 | 支持同线路身份确认 | P0 | 系统可建议，最终由用户确认；跨场馆同色不自动视为同线路 |

### 7.3 姿态与接触事件

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---:|---|
| FR-201 | 输出人体关键点及逐帧置信度 | P0 | 明确显示实际采样 FPS、成功姿态帧数和缺失帧；低置信帧不插值伪装成真实测量 |
| FR-202 | 输出左手、右手、左脚、右脚的岩点接触区间 | P0 | 每个事件可定位到视频时间，并可人工修正 |
| FR-203 | 输出上点、离点、换手、匹配和长停顿候选 | P1 | 事件名称是动作观察，不是技术好坏结论；脚切、脚滑需更高帧率和专项验证后另行准入 |
| FR-204 | 输出尝试开始、结束、完攀/未完攀 | P0 | 用户可修正；计时规则在界面可查看 |
| FR-205 | 生成带岩点、采样骨架和事件标记的复盘视频 | P0 | 采样帧与插值显示在视觉上可区分；可开关叠加层；原画面保持可见；可导出 |
| FR-206 | 自动识别失败时允许完全手工标注关键事件 | P1 | AI 失败不导致整条记录丢失 |

### 7.4 单次复盘指标

第一版只展示从视频中可观察、可复核的指标。

| 指标组 | 指标 | 解释与限制 |
|---|---|---|
| 结果 | 完攀、总用时、动作数 | 必须显示计时起止规则 |
| 接触 | 各肢体接触序列、稳定接触时长、重复触碰/换手 | 来自用户确认后的事件 |
| 节奏 | 移动时间、静止时间、最长停顿、动作间隔 | 停顿不等同于“差”，可能是读线或恢复 |
| 路径 | 身体中点/估计重心轨迹长度、横向摆幅、垂直进展 | 单目视频仅为画面坐标近似；以身高或岩壁标尺归一化 |
| 平滑性 | 速度变化、加加速度的图像域近似 | 对抖动、帧率和遮挡敏感，只用于同条件比较 |
| 姿态 | 肘、肩、髋、膝等二维角度区间 | 非三维关节角，侧身和出平面动作时降低置信度 |
| 对称性 | 左右侧使用比例、左右停留和动作幅度差 | 不把不对称自动判为有害；攀岩线路本身常不对称 |
| 主观反馈 | RPE、疼痛/不适、疲劳、信心、备注 | 由用户自填，健康相关信息单独保护 |

禁止把这些指标合成为一个没有解释的“攀岩水平分”。可以提供分维度趋势，但每个维度都要能回到原视频证据。

### 7.5 历史比较与进步判断

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---:|---|
| FR-301 | 同一线路选择 2–5 次尝试对比 | P0 | 默认只展示同用户、同线路、相似机位记录 |
| FR-302 | 并排/叠加播放并同步关键动作 | P1 | 用户可手工对齐起点或指定共同岩点 |
| FR-303 | 显示指标变化、正常波动区间和置信度 | P0 | 不以单次改善宣布“已进步” |
| FR-304 | 自动生成可解释复盘摘要 | P1 | 每个结论链接到指标和时间点；允许用户隐藏错误结论 |
| FR-305 | 建立个人基线 | P1 | 同线路至少 3 次有效记录后才显示趋势判断 |
| FR-306 | 支持按周/月查看训练量与动作观察项 | P1 | 跨线路只汇总计数型或已标准化指标，不混合原始用时 |

#### 进步判断规则

“精进”应被拆成多个可解释维度：

- 结果进步：由未完攀到完攀，或稳定完攀率提高；
- 效率进步：相同路线下动作数、重复触碰和非必要停顿减少；
- 节奏进步：动作间隔更稳定，长时间犹豫减少；
- 控制进步：经人工确认的脚滑/失控摆动减少，身体中线轨迹在同机位下更平滑；
- 策略变化：手脚顺序或休息点发生变化；
- 主观进步：相同结果下 RPE 或疼痛/不适下降。

系统不得只因“更快”就断言动作更好。若速度提高但脚滑、失控摆动或用户疼痛上升，摘要必须同时展示这些反向证据。

### 7.6 风险观察项

本节是后续产品研究范围，不属于当前 4 FPS 技术原型的上线承诺。风险观察只有在事件级验证集、人工复核和专业顾问评审通过后才可灰度开放；在此之前，用户只能手工标记脚滑、失控摆动、坠落和不适。

风险输出分三层：

| 层级 | 产品措辞 | 示例 | 行为 |
|---|---|---|---|
| 信息 | “动作观察” | 单侧使用明显增多、长时间锁臂、频繁换脚 | 展示证据帧，供用户复查 |
| 注意 | “建议降低强度并复查” | 连续脚滑、快速失控摆动、同一关节角度异常且伴随用户不适 | 建议暂停当前尝试，咨询教练；不作诊断 |
| 紧急提示 | “视频显示可能发生跌落/碰撞事件” | 明显落地失控、头部/肢体碰撞候选 | 提示用户优先确认现实状况；若有伤病症状寻求专业帮助 |

候选观察项包括：

- 连续脚滑或多次失去稳定接触；
- 大幅、快速且未受控的身体摆动；
- 明显落地/碰撞事件；
- 在高速度动作中出现极端二维关节角候选；
- 同一用户多次记录中持续出现的左右差异；
- 用户自报疼痛/不适与特定动作反复同时出现。

必须遵守：

1. 每条提示显示时间点、证据画面、置信度和模型限制。
2. 人物遮挡、关键点低置信、相机角度不适合时不输出强结论。
3. 不从单目画面推断真实冲击力。相关研究表明，视频姿态方案可估计跌落高度和峰值速度，但可能低估峰值加速度；冲击强度仍需要高频 IMU 或力学传感器验证。当前 4 FPS 姿态结果连可靠的瞬时速度峰值也不承诺。
4. 用户可把提示标为“正确/错误/不确定”，用于质量评估；不得默认用于模型训练。

## 8. 数据与权限设计

### 8.1 权限原则

- 默认私密：新视频、新结果和健康相关反馈仅本人可见。
- 最小授权：教练、伙伴或场馆不能因“关注用户”自动获得查看权。
- 所有权隔离：每个业务实体必须有 `owner_id`，服务端每次读取、修改、导出和删除都校验所有权。
- 管理员不可日常浏览：原视频访问采用“应急开锁”机制，必须有工单原因、期限和审计日志。
- 分享可撤销：外链使用短期签名地址，过期或撤销后立即失效。
- 派生数据同权：骨架、轨迹、报告、缩略图和导出文件继承原视频的访问级别。
- 不训练默认：用户数据只有在单独、可撤回的训练授权下才能进入训练集；服务使用同意不等于训练同意。

### 8.2 建议数据实体

以下为独立复盘模块的新实体，不修改照片线路的既有语义：

| 实体 | 主要字段 |
|---|---|
| `climb_replay_attempt` | id, owner_id, route_id?, venue_id?, captured_at, status, review_status, camera_profile_id?, consent_version |
| `climb_replay_media` | attempt_id, media_kind, storage_key, checksum, retention_mode, delete_at, encryption_state |
| `climb_replay_job` | attempt_id, pipeline_version, provider, model_versions, state, progress, cost, error_code |
| `climb_replay_hold_revision` | attempt_id, revision, geometry, source, editor_id, created_at |
| `climb_replay_pose_frame` | attempt_id, timestamp, keypoints, confidence, coordinate_system |
| `climb_replay_event` | attempt_id, type, limb, hold_id?, start_ms, end_ms, confidence, review_state |
| `climb_replay_metric` | attempt_id, metric_key, value, unit, confidence, algorithm_version |
| `climb_replay_observation` | attempt_id, category, severity, evidence_times, explanation, review_state |
| `climb_replay_subjective_feedback` | attempt_id, RPE, discomfort_regions, fatigue, notes, sensitive_flag |
| `climb_replay_share_grant` | attempt_id, grantee_id/link_id, scope, expires_at, revoked_at |
| `climb_replay_audit_log` | actor_id, action, resource_id, purpose, timestamp, result |

所有数据库变更必须使用增量迁移；不得删除、覆盖 `.local/` 中的用户照片、视频、密钥或现有记录。

### 8.3 保存与删除策略

默认策略：

- 上传处理副本：成功分析后 24 小时内删除；失败任务 72 小时内删除，便于用户重试。
- 用户主动选择“保留原视频”：作为私密记录保存，直到用户删除或账户注销。
- 复盘叠加视频：默认保留，用户可单独删除；删除后仍可保留经确认的结构化指标。
- 阿里云处理画面：依据当前官方说明，平台不保存 API 输入输出数据；仍需在产品界面显示供应商、上海地域、处理目的和官方数据保存说明，并定期复核条款变化。
- 删除整次记录：原视频、缩略图、派生视频、姿态、事件、指标、分享链接和缓存均进入删除队列；用户看到完成状态。
- 备份：删除请求需在公开政策承诺的最长期限内从备份过期，不得承诺技术上无法兑现的“立即物理擦除”。

### 8.4 第三方处理与敏感信息

视频中可识别的人脸、身体动作、场馆位置，以及用户自报的疼痛/健康信息，可能构成个人信息；生物识别和医疗健康信息在中国《个人信息保护法》中属于敏感个人信息类别。当前方案只向阿里云上海地域发送降帧后的单张画面，仍需完成第三方处理告知、逐次同意和个人信息保护影响评估。完整视频不得发送给姿态服务；未来如改用境外服务，必须另行完成适用的跨境合规路径。

## 9. 技术方案

### 9.1 推荐架构

```text
Web/移动端
├─ 本地视频预检与可选打码
├─ 分片上传
└─ 结果校正与历史对比
        ↓
复盘 API（账号隔离）
├─ 媒体与保留策略
├─ 任务编排/幂等/取消
├─ 线路只读引用
└─ 审计与授权
        ↓
分析流水线
├─ 九帧中位数背景
├─ 本地专项 Mask R-CNN 岩点掩膜与颜色筛选
├─ 1–10 FPS 抽帧、缩放和 JPEG 压缩
├─ 阿里云 BodyPosture 二维关键点
├─ 关键点标准化与缺失帧标记
├─ 外接框接触规则和基础事件
├─ 指标与可比性判断
└─ 叠加视频渲染（待完成）
        ↓
版本化结果存储
```

当前流水线没有 VLM Run、SAM 3.1 或 ViTPose+ Large 节点。未来更换本地模型或姿态供应商时必须通过统一适配器输出同一版本化结果契约，不得让前端直接依赖供应商响应格式。

### 9.2 模型策略

#### 阶段一：当前混合原型稳定化

- 岩点使用服务器本地专项 Mask R-CNN；姿态使用阿里云 BodyPosture，只对白名单测试账号开放。
- 默认按 4 FPS 抽取 JPEG，最长边不超过 1280 像素、编码质量 82、单张不超过 3 MB；请求速率默认限制为 4 QPS。
- 阿里云返回 18 点后转换为现有 17 点结构；每个缺失采样帧保留零值占位和原视频帧号，不能静默删除。
- 保存本地模型版本、姿态供应商、API 版本、抽帧参数、计划调用数、成功姿态帧数、失败数、费用与耗时。
- 增加岩点、接触、起止时间和完攀状态人工修正；生成结果视频和删除闭环。
- 现有 `prototype_needs_review` 状态保持不变；未经用户确认的姿态和接触初稿不得进入长期趋势。
- 当前缺少阿里云密钥会在本地岩点推理前安全失败；目标产品需允许用户保留视频、稍后重试或进入手工标记，避免第三方服务成为记录功能的单点失败。

#### 阶段二：本地/自托管替代评估

- 姿态估计：评测 MediaPipe、RTMPose/MMPose；代码、权重和训练数据分别登记。
- 岩点：优先使用照片线路的人工确认结果；无线路时评估自托管分割模型。
- 事件检测：保留可解释的规则基线，再用标注数据训练分类器，避免一开始就依赖黑箱大模型。
- 只把独立验证集上达到门槛的模型推入生产。

#### 阶段三：研究增强

- 多机位 3D、Pose2Sim/OpenCap/OpenSim、IMU 或压力/力传感器仅在研究模式使用。
- 研究功能与消费级产品分开，避免把实验性动力学结果包装成健康建议。

## 10. 使用权与许可证审核

5. 第三方云服务合同、隐私、日志、保存地域、数据用途和再训练条款。

- **绿**：当前证据支持内部与商业采用，履行署名/NOTICE 等常规义务即可；

## 11. 非功能需求

### 11.1 隐私与安全

- 传输全程加密，存储使用服务端加密；对象存储 key 不包含用户名或原始文件名。
- 前后端日志不得记录原视频、API 密钥、签名下载链接、健康备注或完整模型响应中的敏感内容。
- API 密钥只存服务端密钥管理，不进入前端、不提交 Git。
- 上传、分析、导出、分享、删除和管理员访问均写审计日志。
- 媒体下载使用短期签名 URL；禁止可枚举路径。
- 对原视频、派生数据和备份执行可验证的删除任务。
- 支持自动人脸/旁观者打码；第一版至少提供手工遮挡区域。

### 11.2 可靠性

- 任务步骤幂等；外部服务超时不产生重复扣费和重复记录。
- 失败时保留用户已完成的线路选择、标注和备注。
- 模型升级不重写历史结果；历史记录保留算法与模型版本。
- 重算产生新版本，用户可以对比并回退到已确认版本。

### 11.3 性能目标

以当前 90 秒/1080p 上限为基准，内部试运营目标：

- 本地预检 10 秒内给出结果；
- 上传后 95% 的可分析视频在 5 分钟内生成初稿；
- 任务排队、运行和渲染阶段均有可理解的进度；
- 单账号并发 1，系统总并发由资源与成本压测后配置；
- 页面在移动端可完成上传、确认、修正和删除操作。

### 11.4 成本目标

- 当前公开按量首档为 0.0016 元/次，BodyPosture 页面列出的按量上限为 5 QPS；代码默认 4 QPS。
- 90 秒视频按 4 FPS 最多计划约 360 次请求，对应姿态接口理论费用约 0.576 元/次任务；这只是按当前公开首档计算的估算，不含失败重试、服务器、本地推理、存储和带宽。
- 每个任务必须保存计划调用数、实际请求数、成功姿态帧数和估算费用；账单监控以阿里云实际结算为准。
- 设置账号日调用上限、全局月预算和异常熔断；超过预算时进入排队或手工模式，不得无限自动重试。
- 在验证集上比较 2、4、6 FPS 的准确率增益与成本，只有指标收益显著时才提高默认 FPS。

### 11.5 可访问性与解释性

- 颜色不是唯一状态表达；线路颜色需有文字名称或编号。
- 时间轴事件可通过键盘选择；叠加层可单独开关。
- 每个指标可查看定义、单位、数据范围、置信度和“不适用”原因。
- AI 摘要不得隐藏原始证据或人工修改历史。

## 12. 质量与上线验收

### 12.1 验证集设计

建立有明确授权的独立测试集，至少覆盖：

- 40 段以上视频、10 名以上不同体型/衣着的攀岩者；
- 不同岩壁颜色、灯光、遮挡、相机距离和手机型号；
- 静态、动态、侧身、脚切、脚滑、坠落/落地等动作；
- 成功与失败尝试；
- 不包含在训练集中的线路与人物。

由至少两名人工标注者独立标注岩点、手脚接触、起止时间、完攀和风险观察事件；存在分歧时仲裁并记录一致性。

### 12.2 生产准入门槛

以下是目标门槛，不代表当前系统已经达到：

| 项目 | 最低门槛 |
|---|---:|
| 合格视频任务成功率 | ≥ 95% |
| 可见关键点覆盖率 | ≥ 90% 的适用帧 |
| 手脚—岩点接触事件 F1 | ≥ 0.85 |
| 完攀状态准确率 | ≥ 95% |
| 起止计时平均绝对误差 | ≤ 1.0 秒 |
| 高风险观察项误报率 | ≤ 10%，且必须人工复核 |
| 删除请求任务成功率 | 100% |
| 跨账号越权自动化测试 | 0 个通过攻击样例 |
| 许可证、权重和数据来源缺项 | 0 项 |
| 多人画面主体切换率 | 上线范围内为 0；否则拒绝分析 |
| 抽样帧数据去向与同意记录缺项 | 0 项 |

不同拍摄条件分别报告结果，不允许只发布总体平均数掩盖某些人群、肤色、衣着、光照或体型上的明显退化。

### 12.3 必须阻止输出的情况

- 人体关键点长期低置信；
- 人物离开画面或多人无法稳定跟踪；
- 镜头移动导致岩点坐标失效；
- 线路未确认；
- 帧率或画质不足；
- 关键身体部位严重遮挡；
- 多人画面无法确认同一主体；
- 模型/权重版本未登记；
- 用户未同意本次向阿里云发送抽样画面；
- 试图从当前 4 FPS 结果输出自动脚滑、碰撞峰值或伤害风险结论。

此时系统应显示“本视频不适合可靠分析”，而不是生成看似完整的评分。

## 13. 发布计划

### 阶段 A：内部可用版（建议 2–3 周）

**需要采纳/借鉴：** OSS-01、OSS-02、OSS-03、OSS-05、OSS-06、OSS-12；P-01、P-06、P-07；OFF-01–04；LOCAL-01–03。重点借鉴事件与报告契约、视频质量门和姿态替代评测；本阶段同时补齐本地模型权利链、云接口证据和服务端同意记录。

- 固化“本地岩点 + 阿里云抽帧姿态”结果契约，并删除复盘模块所有历史 VLM 配置说明；
- 把前端同意升级为服务端可审计记录，拒绝缺少同意版本的任务进入姿态调用；
- 补齐结果叠加视频；
- 增加岩点、接触、时间和完攀人工修正；
- 落实处理副本删除与保留选项；
- 每次任务记录本地模型版本、阿里云 API 版本、抽帧参数、实际调用量、成本和耗时；
- 阿里云不可用时允许保存视频并稍后重试，不丢失用户记录；
- 建立 10–20 段自有授权样本做基线评测；
- 只对内部白名单开放。

退出条件：数据不丢、可删除、可解释、可修正；不要求风险提示上线。

**研究沉淀：** 保存授权样本、标注规范、失败样例、模型/规则版本、2/4/6/10 FPS 与 0.4/0.5 秒接触阈值消融、分项准确率、成本和时延；可作为以后论文中的系统方法与基础实验材料。

### 阶段 B：个人历史与同线路对比（建议 3–5 周）

**需要采纳/借鉴：** OSS-02、OSS-03、OSS-04、OSS-08；P-04、P-05、P-10、P-15。重点借鉴同线路对齐、二维轨迹/节奏指标和个体内多维解释；明确静止不一定是差动作，二维身体中点也不等于真实三维重心。

- 正式持久化确认后的尝试；
- 同线路 2–5 次对比；
- 分维度趋势与主观反馈；
- 相似机位检测与不可比提示；
- 数据导出、分享授权和撤销。

退出条件：至少 3 次记录才能给趋势结论；所有结论可回到证据帧。

**研究沉淀：** 保存机位可比性、重复测量可靠性、用户修正前后指标和主观反馈；可用于研究同路线重复尝试中的接触序列、停顿、轨迹与 RPE 变化。

### 阶段 C：安全观察试验（建议 4–8 周）

**需要采纳/借鉴：** OSS-07、OSS-09、OSS-10、OSS-11；P-02、P-03、P-08、P-09、P-11、P-12、P-14。重点借鉴标定多机位、三维运动学、高速视频和 IMU 联合验证，不能把这些研究的能力外推给当前 4 FPS 单目原型。

- 单独评估更高采样率、本地视频姿态或传感器方案，不能直接沿用 4 FPS 原型输出安全结论；
- 与教练/运动医学顾问共同定义观察项；
- 建立独立事件测试集；
- 先上线信息级提示，再灰度注意级提示；
- 评估误报、漏报、用户理解和是否诱发错误安全感。

退出条件：达到误报门槛，文案通过专业与合规评审，界面持续显示非医疗声明。

**研究沉淀：** 保存同步高帧率视频/IMU 真值、专业事件标签、误报漏报和用户理解测试；可用于以后研究视频高度/速度估计与 IMU 冲击峰值之间的差异。

### 阶段 D：商业发布准备

**需要采纳/借鉴：** 全部 OSS 许可证记录、OFF-01–05、LOCAL-01–03。论文仅用于技术依据和局限说明，不能替代正式合同、人物授权、数据许可和法律审核。

- 阿里云服务合同、数据处理评估、地域配置和计费上限完成归档；
- 模型、权重、数据、代码台账全部为绿或经书面例外批准；
- 完成 SBOM、第三方 NOTICE、隐私政策、用户协议和删除演练；
- 通过权限、越权、上传、对象存储和密钥安全测试；
- 完成真实成本模型和容量压测；
- 明确事故响应和投诉处理负责人。

**研究沉淀：** 固定 SBOM、NOTICE、模型与数据哈希、条款快照、真实账单和上线验收报告。只有在用户另行同意研究且完成伦理、隐私和授权评估后，服务数据才可作为部署研究材料。

## 14. 成功指标

### 14.1 产品指标

- 有效视频完成复盘率；
- AI 初稿被用户确认的比例；
- 每次复盘的平均人工修正数量；
- 用户在 30 天内完成第二次同线路记录的比例；
- 用户打开证据帧、播放叠加视频和使用对比功能的比例；
- 错误提示反馈率及被纠正后的净准确率；
- 原视频保留、导出和删除的完成率。

### 14.2 质量指标

- 岩点、姿态、接触、完攀和计时的分项准确率；
- 风险观察项逐类误报率与漏报率；
- 不同设备、光照、肤色、衣着、体型和动作风格的性能差异；
- 单任务平均成本、P50/P95 耗时和失败重试成本；
- 用户修正后趋势结论发生变化的比例。

### 14.3 不采用的虚荣指标

- 不以总上传量代替有效复盘率；
- 不以 AI 生成报告字数衡量价值；
- 不以单一“进步分”作为核心指标；
- 不以用户忽略安全提示作为安全成功。

## 15. 主要风险与缓解

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 单目视频无法测真实发力 | 用户误以为得到生物力学测量 | 使用“动作代理指标”；明确限制；研究版再接 3D/IMU |
| 遮挡、侧身导致姿态错误 | 接触与角度误判 | 质量门、逐帧置信度、人工修正、不可分析状态 |
| 安全提示误报/漏报 | 焦虑或错误安全感 | 只输出可观察事件；证据帧；专业评审；分级灰度 |
| 第三方画面处理边界不清 | 隐私和第三方处理风险 | 只发送降帧 JPEG；记录本次同意；归档阿里云数据处理说明；完整视频留在本系统 |
| 开源顶层许可证掩盖传递依赖 | 商业侵权风险 | SBOM、权重台账、传递依赖扫描、红线依赖阻断 |
| 研究数据集可下载但不可商用 | 训练数据权利瑕疵 | 隔离研究；未获书面许可不进产品训练集 |
| 同路线身份判断错误 | 趋势失真 | 用户确认、场馆/墙面/线路版本共同识别 |
| “更快”被误读为“更好” | 鼓励冒险动作 | 多维结果、同时展示失控/疼痛/脚滑证据 |
| 用户数据被误上传 GitHub | 严重泄露 | 禁止自动同步；提交前密钥和大文件扫描；`.local/` 永久排除 |
| 模型升级改变历史 | 趋势不可解释 | 保存模型/算法版本；新版本只生成新修订 |

## 16. 待决策事项

商业上线前必须由产品负责人明确以下选择：

1. 产品是否继续保持个人自用，还是计划对外收费；两者的权利和合规成本不同。
2. 是否接受阿里云 BodyPosture 的按量成本和第三方处理条款，或投入本地姿态模型替代。
3. 原视频的默认策略：本 PRD 建议“不默认长期保留，用户明确选择才保留”。
4. 是否允许 14 周岁以下未成年人使用；如允许，需要监护人机制和更严格的数据处理设计。
5. 教练复核属于点对点分享，还是未来场馆组织功能；后者需要组织权限模型和合同。
6. 安全观察项由哪位具备资质的教练、运动医学或康复专家负责定义与复核。
7. 项目对外分发时采用何种自有代码许可证，以及贡献者版权如何归集。

## 17. 交付定义（Definition of Done）

一个版本只有同时满足以下条件才算完成：

- 功能有用户路径、失败路径和删除路径；
- 分析结果可定位到视频证据并可人工修正；
- 照片线路默认链路没有被改变；
- 不读取、覆盖、删除或上传 `.local/`；
- 新实体全部 `owner_id` 隔离，越权测试通过；
- 模型、权重、数据集、代码和云服务均进入权利台账；
- 许可证/NOTICE 随构建交付；
- 原视频与派生数据保留策略可以被系统实际执行；
- 用户能导出和删除自己的记录；
- 质量门槛在独立授权测试集上达标；
- 所有安全提示均为观察性措辞，没有医学诊断或安全保证；
- 部署到生产环境另有明确部署任务和批准，不因合并代码自动部署。

## 19. 最终产品决策

**建议批准继续开发，但批准范围限定为“内部可用版 + 个人历史对比”，不批准直接商业上线安全诊断。**

最优先的产品工作不是增加更多模型，而是补齐四个闭环：

1. 本地岩点与阿里云抽帧姿态结果的可视化、人工修正与版本化；
2. 同线路、同条件、同采样参数下的长期可比性；
3. 原视频、发送帧、派生数据的告知、授权、留存与删除；
4. 自有模型、训练数据、阿里云服务和开源依赖的完整权利台账。

完成这四项后，再投入安全观察模型，才能避免做出一个“看起来聪明、实际上不可复核且权利不清”的产品。
