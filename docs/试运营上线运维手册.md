# 攀岩定线系统试运营上线运维手册

## 一、适用范围

本手册只适用于 1–5 人、30 天的小范围真实试运营：

- 电脑端 Chrome/Edge 支持完整编辑，手机仅保证查看。
- 开放总览、定线工作台、岩点库、岩板资产、标准板库和 AI 实验室。
- 仿真功能通过前端 `VITE_ENABLE_SIMULATION=false` 隐藏，并由后端 `ENABLE_SIMULATION=false` 拒绝直接请求。
- 使用共享本地数据；Supabase 必须保持停用。
- AI 只润色文字；没有合格供应商或外部服务失败时，继续使用本地规则结果。

任何公网开放、超过 5 人、正式账号或权限隔离都不属于本次上线。

## 二、职责和门禁

| 角色 | 负责 | 不负责 |
|---|---|---|
| 产品与数据负责人 | 确认真正要迁入的数据、上线时间、最终验收 | 安装软件、执行命令、判断服务器错误 |
| 发布操作员 | 测试、备份、部署、回退、记录和日常检查 | 擅自删除或恢复数据 |
| 试运行人员 | 单人编辑同一岩板、报告异常、避免输入个人信息 | 修改服务器、分享访问账号 |

没有以下资源时不得发布：

- 云控制台、SSH 和安全组权限；
- GitHub 发布标签读取权限；
- Tailscale 管理账号及个人成员账号；
- 私有对象存储桶、版本控制、服务端加密、30 个每日和 6 个每月版本的生命周期策略；
- 独立受限的 rclone 对象存储凭据；
- 应急管理电脑和云控制台登录方式；
- 如启用 AI：明确供应商地址、密钥、模型、数据条款和余额上限。

## 三、发布前代码门禁

当前工作区包含大量尚未提交的既有改动，不能直接打标签。发布操作员必须：

1. 在 `codex/pilot-release-hardening` 分支逐项审查差异。
2. 将程序、文档、演示数据、真实数据和生成文件分类；`.env`、密钥、虚拟环境和依赖目录不得进入 Git。
3. 运行：

```powershell
cd backend
.\.venv\Scripts\python.exe -m unittest `
  test_ai_lab_experiments `
  test_hold_image_processing `
  test_local_only_mode `
  test_release_hardening `
  test_release_readiness `
  test_standard_board `
  test_standard_board_activity `
  test_standard_board_difficulty `
  test_standard_board_local_first `
  test_standard_board_tags

cd ..\frontend
npm.cmd ci
$env:VITE_ENABLE_SIMULATION='false'
npm.cmd test
npm.cmd run build
```

4. 提交后通过 GitHub `release-gate` 的 Ubuntu 24.04、Python 3.12、Node 24 验证。
5. 只给通过审查的提交创建 `pilot-v<版本>` 标签。标签创建后不修改、不复用。

## 四、服务器首次建设

### 1. 环境检查

使用项目规定的 GitHub 到服务器同步方式取得源码后，在 `/root/ai_climbing_code` 运行：

```bash
sudo ./deploy/scripts/server_preflight.sh
```

必须全部通过：Ubuntu 24.04 LTS、systemd、Git、rsync、Nginx、Python 3.12、Node 24、Tailscale、rclone、curl、tar、sha256sum 和 flock。任何失败都先修复，不带病上线。

若检查报告存在其他 Nginx `listen`，先备份并停用旧站点配置，再重新运行门禁；本项目只接受 `127.0.0.1:8080`，不能保留默认的 `0.0.0.0:80` 或 `[::]:80`。

安装生产配置：

```bash
sudo ./deploy/scripts/install_server_assets.sh
```

脚本会建立专用服务账号和固定目录，但不会自动公开网站或填入密钥。

### 2. 私有网络

1. 所有成员使用个人 Tailscale 账号，不共用账号。
2. 将 `deploy/tailscale/policy.example.hujson` 中的示例邮箱替换为真实成员，在管理后台验证策略后保存。
3. 服务器使用中性名称和 `tag:ai-climbing`：

```bash
sudo tailscale up --hostname=climbing-pilot --advertise-tags=tag:ai-climbing
```

4. 启用 MagicDNS/HTTPS 后，将私有 HTTPS 转发至本机 Nginx：

```bash
sudo tailscale serve --bg http://127.0.0.1:8080
sudo tailscale serve status
```

禁止使用 `tailscale funnel`。任何必需设备无法稳定连接时停止上线，改用自建 WireGuard；不得开放公网端口替代。

### 3. 云安全组

- 公网入站关闭 80、443、8000、8080 和 5173。
- Tailscale 验证成功且云控制台应急入口可用后，关闭公网 22。
- 从未授权网络实际访问公网 IP，必须连接失败。
- Nginx `nginx -T` 中本项目只能看到 `127.0.0.1:8080`。

### 4. 对象存储

1. 创建私有桶，开启版本控制和服务端加密。
2. 生命周期：每日备份保留 30 天，每月备份保留 6 个月。
3. 创建仅允许目标前缀读、写、列举的独立凭据；旧版本删除由桶生命周期执行。
4. 用 root 配置 `/etc/ai-climbing/rclone.conf`，权限 `0600`。
5. 将 `/etc/ai-climbing/backup.env` 的 `RCLONE_REMOTE` 设置为 `remote-name:bucket/prefix`。
6. 先执行一次：

```bash
sudo /usr/local/lib/ai-climbing/backup_data.sh manual
```

人工本地备份允许没有远端；每日和发布前备份没有远端时会失败。

### 5. 生产环境变量

编辑 `/etc/ai-climbing/backend.env`，必须保留：

```dotenv
APP_ENV=production
LOCAL_ONLY=true
DISABLE_SUPABASE=true
ENABLE_SIMULATION=false
```

AI 未获批准时，`OPENAI_API_KEY`、`OPENAI_BASE_URL`、`LLM_MODEL_NAME` 全部留空。批准后必须三个值都明确填写；线路名称和说明中不得包含姓名、电话等个人信息。

## 五、首次数据迁移

1. 在独立审核副本检查现有 `backend/data`，确认哪些岩板、岩点、图片和记录属于试运营。
2. 原服务器数据先做只读副本；不得在审核过程中覆盖原文件。
3. 目标 `/var/lib/ai-climbing/data` 必须为空。
4. 执行：

```bash
sudo /usr/local/lib/ai-climbing/migrate_pilot_data.sh \
  /root/ai_climbing_code_review/approved/backend/data
```

脚本只接受约定审核路径、验证关键文件、生成全文件校验清单，并拒绝覆盖非空目标。迁移记录保存在 `/var/lib/ai-climbing/migrations`。

## 六、固定发布流程

1. 在《试运营发布检查单》登记标签、提交号、变更、上一版本、回退人和维护窗口。
2. 通知全部成员停止编辑，确认没有正在运行的 AI 任务。
3. GitHub 发布门禁必须通过。
4. 在 03:00–04:00 执行：

```bash
sudo /usr/local/lib/ai-climbing/deploy_release.sh pilot-v<版本>
```

脚本会：

- 从指定 GitHub 仓库检出不可变标签；
- 同步到 `/root/ai_climbing_code`；
- 使用 `npm ci` 和锁定 Python 依赖构建新版本；
- 强制关闭仿真并运行自动化测试；
- 在 `127.0.0.1:8001` 验证健康接口和生产调试文档关闭；
- 对已有生产服务先做异地发布前备份；
- 写入新版本目录并原子切换 `/opt/ai-climbing/current`；
- 失败时自动切回上一程序版本，绝不回退数据。

5. 从授权电脑依次验证：
   - 私有 HTTPS、总览和导航；
   - 岩点图片；
   - 新建、保存、更新、归档和恢复岩板；
   - 标准线路名称/来源搜索和载入工作台；
   - 岩板对照；
   - AI 组合或审核；
   - 临时清空 AI 配置后仍能返回本地规则结果；
   - `/docs`、仿真入口和仿真 API 不可用。
6. 观察 30 分钟并登记结果。保存失败、数据异常、公网可访问或核心页面不可用时立即回退。

## 七、程序回退和数据恢复

程序回退不触碰数据：

```bash
sudo /usr/local/lib/ai-climbing/rollback_release.sh pilot-v<上一版本>
```

数据恢复属于高风险操作。先停止写入、保留故障现场、下载备份和 `.sha256`，再执行：

```bash
sudo /usr/local/lib/ai-climbing/restore_data.sh /var/backups/ai-climbing/daily/<备份>.tar.gz
```

脚本会显示项目规定的高风险说明，只有交互输入准确的 `确认执行` 才继续。旧数据会移入隔离目录而不是删除；新数据健康检查失败时自动放回旧数据。

每次恢复后核对：

- 校验文件通过；
- 岩板总数、归档数和关键样例；
- 岩点元数据、图片和轮廓；
- 标准线路活动记录；
- 后端重启后数据仍在。

## 八、日常、每周和第15天操作

每天 03:15 systemd 自动停止写入、打包全量数据、上传对象存储、重新下载校验、重启并检查健康。每五分钟记录一次本机可用性。

每天 09:00 发布操作员必须运行：

```bash
sudo /usr/local/lib/ai-climbing/daily_check.sh
```

全部通过后才允许批量编辑或更新。还要在对象存储控制台人工确认版本与生命周期、检查 AI 余额和未解决问题。

每周：

- 安全更新和磁盘增长；
- Tailscale 成员及设备，离组或丢失设备当天撤销；
- AI 费用、失败次数和数据输入规范；
- 关键变更登记与问题关闭情况。

上线前和第 15 天必须把备份恢复到隔离目录或隔离服务器，完成 4 小时恢复演练；不得覆盖生产数据。

## 九、30天验收

只有同时满足以下条件才允许讨论扩大范围：

- 30 次每日异地备份全部成功；
- 无公网暴露、严重安全事件或不可恢复数据损坏；
- 五分钟健康记录可用率不低于 98%；
- 恢复演练满足最多丢失 24 小时、4 小时内恢复；
- 核心流程得到试运行人员确认，严重问题全部关闭。

公开联网或超过 5 人必须另行完成正式账号、角色权限、操作审计、数据库并发、自动告警、隐私条款和公网安全测试。
