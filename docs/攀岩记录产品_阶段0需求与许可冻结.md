## 0. 本阶段结论

阶段 0 的六项交付物已经形成：完整用户旅程、页面清单、状态清单、数据字典、算法与素材许可台账、电子岩板退出与旧数据无损迁移方案。

当前决策是：

- 第一版产品只解决“拍照 → 识别 → 人工确认 → 编辑 → 保存 → 复盘”的个人闭环。
- 普通用户入口使用“攀岩记录 / 我的线路”心智，不出现定线、电子岩板、孔位、仿真或 AI 实验室。
- 原照片始终保留，模型原结果与用户确认结果分开保存。
- 社区、同线聚合、自动难度、动作推测、墙面净化和人物移除不进入第一版。
- 现有专项模型权重许可保持红灯；许可转绿前只能用于本地研究和封闭原型，不能据此收费或宣传商业可用。
- 旧照片、旧数据库与 `.local/` 不删除、不覆盖、不自动重算。迁移采用可重复、可核对、可回滚的新增式迁移。
- 本文确认前不进入 Figma；Figma 流程确认并冻结前不进入前端开发。

这是一份工程与产品冻结文件，不替代律师出具的法律意见。

## 1. 产品合同

### 1.1 一句话价值

拍一张线路照片，几分钟内得到一张可长期保存、标记、复盘和补充攀爬影像的个人线路卡片。

### 1.2 第一版目标用户

- 在岩馆攀爬、希望记住线路和卡点的普通攀岩者。
- 主要使用手机拍摄和记录，也会在电脑上查看或补充内容。
- 不要求用户理解定线、电子岩板、模型或计算机视觉术语。

### 1.3 第一版必须完成

- 邀请注册与登录。
- 我的线路空状态、列表、筛选与恢复入口。
- 手机拍照或相册选择，拍后立即建立本地草稿。
- 用户确认后上传并启动服务端识别。
- 显示识别进度、失败、取消、重试和恢复。
- 在原图上增删路线成员、补点、修正轮廓。
- 原图编辑器、单点备注、起终点和顺序、自由标记、撤销与重做。
- 路线资料、难度、攀爬日志、图片与视频。
- 自动保存、版本冲突提示、刷新和重启恢复。
- 保存为私密个人线路卡片，再次打开默认浏览状态。

### 1.4 第一版明确不做

- 社区、公开帖子、同线聚合、评论、收藏、关注、点赞和私信。
- 自动判断动作、起终点、顺序或难度。
- 电子岩板转换、孔位推断、墙面投影或岩板资产管理。
- 墙面净化、人物移除、不可见内容生成。
- DeepSeek 或其他云端视觉复核进入默认照片识别链路。
- 把模拟数据、开发样本结果或人工修正结果宣传为模型准确率。
- 正式生产部署或商业收费。

### 1.5 成功指标

| 指标 | 第一版验收口径 |
| --- | --- |
| 首条记录耗时 | 从选择照片到保存有效记录不超过 3 分钟，人工犹豫时间单列 |
| 可操作预览 | 正常情况下尽量在 30 秒内进入；超时不得阻塞原图和草稿保存 |
| 最小有效记录 | 原图、确认后的路线岩点、难度或一条备注 |
| 可修正性 | 不重新上传照片即可修正漏点、误点和轮廓 |
| 恢复性 | 刷新、断网、关闭页面和服务重启后，已完成步骤不丢失 |
| 识别声明 | 独立留出门禁未通过前，不宣称商业可用或达到 90% |

## 2. 完整用户旅程

### 2.1 主成功路径

1. 用户使用一次性邀请码注册或登录。
2. 首次进入独立“攀岩记录”入口，只看到“拍照片、确认路线、保存复盘”三件事。
3. 用户在“我的线路”点击“拍照记录线路”，或使用固定底部导航的“拍照”。
4. 页面用一屏内的简短示意提示完整入镜、避免严重倾斜、尽量减少人物遮挡。
5. 用户调用相机或从相册选图。
6. 设备立即保存原图引用和本地草稿；用户可先填名称、场馆、墙面区域和备注。
7. 有网络时，用户明确点击“上传并识别”。系统不得在未确认时偷偷上传或消耗流量。
8. 服务端依次检查照片、识别岩点、执行轮廓内分色，并返回全部候选。
9. 用户选择目标颜色或目标路线，进入复核。
10. 用户在原图上删除误点、补加漏点、调整轮廓，并确认最终路线成员。
11. 用户可标记起点、终点和顺序，给单个岩点添加备注，也可用画笔、箭头、圆圈和文字做自由标记。
12. 用户填写难度、总备注和首次攀爬日志，按需补充图片或视频。
13. 自动保存持续工作；用户点击“完成记录”后生成私密线路卡片。
14. 用户再次打开线路时先进入浏览状态，主动点击“编辑”后才出现修改工具。

### 2.2 弱网与离线路径

1. 选图后先建立本地草稿，不等待网络。
2. 离线时仍可编辑标题、场馆、墙面区域和总备注。
3. 草稿在“我的线路”中显示“仅保存在此设备”，不能藏在错误提示里。
4. 网络恢复后提示用户确认上传；不自动开始大文件传输。
5. 上传失败保留原图、本地字段和已完成分片，允许继续或重试。
6. 若用户换设备，本地未上传草稿不会自动出现；界面需明确说明这一边界。

### 2.3 识别失败与恢复路径

1. 照片上传成功后即形成可恢复的服务端记录壳，识别失败不得丢失照片。
2. 识别可取消、超时和重试；同一幂等请求不得重复创建记录。
3. 服务重启后，排队或处理中任务恢复为“可继续”或“可重试”，不能永久卡在处理中。
4. 自动识别无可用结果时，用户仍可在原图上点选漏点或手动画轮廓。
5. 失败状态进入首页列表，并提供“继续编辑照片”和“重新识别”两个不同动作。

### 2.4 冲突路径

1. 每次写入携带记录版本号和幂等请求号。
2. 服务端发现版本落后时拒绝覆盖，并返回当前版本摘要。
3. 用户可以选择保留本机版本、使用云端版本，或在字段级冲突页逐项确认。
4. 媒体上传和文本保存独立重试，单个媒体失败不得回滚已保存的线路数据。

### 2.5 删除路径

1. 第一版“删除线路”实现为归档，可从回收/归档入口恢复。
2. 永久删除个人记录、原图或媒体需要二次确认，并说明关联内容影响。
3. 未来存在公开快照时，删除私密原记录不得暗中改写已发布快照；二者按单独规则处理。
4. 旧数据库实体、旧 `.local/` 文件和生产数据不属于普通用户删除流程。

## 4. 状态清单与状态机

### 4.1 记录主状态

| 状态代码 | 用户文案 | 可执行动作 | 退出条件 |
| --- | --- | --- | --- |
| `local_draft` | 仅保存在此设备 | 编辑、放弃、准备上传 | 用户确认上传 |
| `waiting_upload` | 等待上传 | 上传、继续编辑、放弃 | 开始传输 |
| `uploading` | 正在上传照片 | 后台继续、取消 | 上传完成或失败 |
| `checking_photo` | 正在检查照片 | 后台继续、取消 | 质量检查完成 |
| `recognizing_holds` | 正在识别岩点 | 后台继续、取消 | 返回候选或失败 |
| `awaiting_route_choice` | 请选择目标线路 | 选颜色/候选、手工开始 | 进入复核 |
| `reviewing_holds` | 请确认线路岩点 | 增删、补点、修轮廓、确认 | 用户确认成员 |
| `editing_record` | 正在完善记录 | 编辑、添加日志/媒体、完成 | 用户完成记录 |
| `saved` | 已保存 | 浏览、编辑、追加日志 | 显式进入编辑或归档 |
| `archived` | 已归档 | 恢复、永久删除 | 恢复或确认永久删除 |
| `failed_recoverable` | 照片已保存，识别未完成 | 手工编辑、重试 | 有可用成员或放弃 |
| `conflict` | 发现其他设备的更新 | 对比、选择、合并 | 产生新版本 |

### 4.2 独立子状态

- 网络：`online`、`offline`、`reconnecting`。
- 自动保存：`clean`、`dirty`、`saving`、`saved`、`save_failed`、`conflict`。
- 上传队列：`queued`、`uploading`、`paused`、`retryable`、`completed`、`cancelled`。
- 识别任务：`queued`、`running`、`cancel_requested`、`cancelled`、`failed`、`completed`。
- 媒体：`local_only`、`authorizing`、`uploading`、`verifying`、`ready`、`failed`、`deleted`。
- 权限：`unknown`、`granted`、`denied`、`blocked`。

### 4.3 状态约束

- 原图一旦服务端接收成功，识别失败不得让记录回到“不存在”。
- 模型候选确认前后是两个不同数据快照；不能用人工结果覆盖模型原结果。
- 完成记录不等于不可编辑；后续编辑产生新版本。
- `saved`、`archived` 和公开状态相互独立。第一版没有公开状态。
- 前端展示文案使用人话，状态代码只存在于实现和接口中。

## 5. 数据字典

### 5.1 坐标与版本公共规则

- 所有轮廓、点、箭头、圆圈、文字锚点都以原图宽高归一化为 `[0, 1]` 坐标。
- 原图保留原始字节和 SHA-256；派生预览、缩略图和公开快照不得覆盖原图。
- 所有可变聚合带单调递增 `version`；所有写请求带唯一 `request_id`。
- 所有业务数据带 `owner_id`，服务端按当前账号校验所有权，不能信任前端传入的 owner。
- 时间统一以 UTC ISO 8601 存储，展示时转换为用户本地时区。

### 5.2 核心实体

| 实体 | 关键字段 | 约束 / 说明 |
| --- | --- | --- |
| `photo_record` | `id`, `owner_id`, `version`, `status`, `title`, `grade_system`, `grade_value`, `grade_text`, `gym`, `wall_area`, `route_color`, `notes`, `created_at`, `updated_at`, `archived_at` | 第一版核心聚合；默认私密；一条记录对应一张原始照片和一条路线 |
| `original_photo` | `id`, `record_id`, `storage_key`, `sha256`, `mime`, `bytes`, `width`, `height`, `captured_at`, `created_at` | 永久保留且不可被派生文件覆盖；访问必须校验所有权 |
| `recognition_run` | `id`, `record_id`, `attempt`, `status`, `stage`, `progress`, `model_card_id`, `model_version`, `config_digest`, `input_digest`, `started_at`, `finished_at`, `error_code` | 可取消、可重试；每次重试新增 run，不覆盖历史 run |
| `recognized_hold` | `id`, `run_id`, `kind`, `color_group`, `contour`, `bbox`, `confidence`, `mask_asset`, `cutout_asset`, `created_at` | 只保存模型原结果；不写入用户确认信息 |
| `confirmed_hold` | `id`, `record_id`, `source_hold_id`, `origin`, `color_group`, `contour`, `ordinal`, `roles`, `note`, `version`, `updated_at` | `origin` 为 `model` 或 `manual`；用户确认结果，可修正但保留版本 |
| `annotation` | `id`, `record_id`, `type`, `geometry`, `style`, `text`, `z_index`, `version`, `created_at`, `updated_at` | 类型为画笔、箭头、圆圈或文字；归一化坐标 |
| `ascent` | `id`, `record_id`, `climbed_on`, `completed`, `attempts`, `notes`, `created_at`, `updated_at` | 多次日志只追加或单条编辑，不覆盖其他历史日志 |
| `media_item` | `id`, `record_id`, `kind`, `storage_key`, `mime`, `bytes`, `width`, `height`, `duration_ms`, `ordinal`, `status`, `created_at` | 每条最多 8 图、2 视频；原图计入图片总数；默认私有 |
| `edit_revision` | `id`, `record_id`, `record_version`, `snapshot_digest`, `change_summary`, `created_at` | 支持恢复和审计；不存秘密字段 |
| `idempotency_receipt` | `owner_id`, `scope`, `request_id`, `response_digest`, `created_at` | 防止重复创建和重复保存；组合键唯一 |
| `upload_part` | `id`, `media_id`, `part_no`, `bytes`, `digest`, `status`, `updated_at` | 支持断点续传；本地和服务端均不得保存密码或邀请码 |

### 5.3 未来兼容但第一版不创建的实体

- `public_snapshot`：发布时生成的不可变公开副本。
- `same_route_candidate`：同线候选与用户确认，不自动合并。
- `post`、`comment`、`favorite`、`report`：社区第二阶段。

第一版仅保留命名和外键扩展空间，不创建社区页面、接口或空表。

## 6. 现有数据映射与无损迁移

### 6.1 现有实现事实

当前本地实现使用 SQLite 与本地资产目录，照片工作流主要落在：

- `photo_work_sessions` / `photo_work_receipts`：当前单线路工作状态与幂等回执。
- `board_versions`：原照片、尺寸、质量、模型版本和处理状态。
- `board_objects`：岩点轮廓、颜色、掩膜、裁图和复核状态。
- `processing_jobs`：识别任务。
- `routes` / `route_members` / `route_revisions`：线路资料、成员和版本。
- `object_anchors`：电子岩板孔位映射，目标产品不使用。
- `background_variants`：墙面净化派生物，目标产品不使用。
- 旧 `drafts.json` 与提取目录：历史草稿兼容来源。

### 6.2 映射合同

| 旧数据 | 新数据 | 迁移规则 |
| --- | --- | --- |
| `board_versions` | `photo_record` + `original_photo` | 一张有效原图生成一条记录；保留旧 ID 为 `legacy_source_id` |
| `processing_jobs` | `recognition_run` | 历史任务只读导入；不把失败任务伪装为成功 |
| `board_objects` | `recognized_hold` | 原始模型对象进入模型快照；人工新增对象需按来源判断进入 `confirmed_hold` |
| `routes` | `photo_record` 元数据 | 名称、难度、备注、状态和版本映射；`setter` 不进入普通用户主界面 |
| `route_members` | `confirmed_hold` | 成员、顺序、起终点和单点备注映射 |
| `route_revisions` | `edit_revision` | 保留旧快照摘要和版本，不在迁移时覆盖当前版本 |
| `photo_work_sessions` | 恢复上下文 | 只用于恢复未完成流程，不作为长期产品主表 |
| `object_anchors` | 不迁移到新交互 | 原表只读保留；新接口和页面不返回孔位 |
| `background_variants` | 不迁移到新交互 | 原表和资产只读保留；不生成新净化结果 |
| 旧草稿 JSON | `photo_record` 本地/服务端草稿 | 显式导入；按指纹去重；源文件不移动、不删除 |

### 6.3 迁移顺序

1. 对旧数据库与资产目录做只读盘点，记录数量、所有者、文件指纹和孤立引用；不输出真实用户内容。
2. 创建新的迁移表和 `legacy_source_id` 唯一约束；不改旧表含义。
3. 先迁移单个测试账号的副本，使用同一事务写入记录、照片、候选和成员。
4. 重复运行迁移必须得到相同结果，不能重复创建记录或媒体。
5. 对每个账号核对记录数、成员数、原图 SHA-256、归档状态和版本数。
6. 新入口先双读：优先读新记录，未迁移记录通过兼容适配器只读展示。
7. 完成移动端、桌面端、重启恢复和权限隔离验收后，才切换新入口写入。
8. 旧入口、旧表、旧资产和 `.local/` 长期只读保留；物理删除另立任务并按高风险删除流程确认。

### 6.4 回滚与数据安全

- 迁移只新增，不更新或删除旧记录，所以回滚是停用新入口并回到旧读取路径。
- 每批迁移前生成数据库文件级备份和资产清单；备份路径不进入 Git。
- 任何数据库表、字段、函数、触发器、策略、存储桶或真实文件删除，都必须另列目标、影响、数据损失、恢复方式和备份位置，并等待用户明确回复“确认执行”。
- `.local/` 中照片、模型、密钥和用户数据不得复制到仓库、日志或公开文档。

### 7.1 第一轮移除的是“普通用户暴露面”
